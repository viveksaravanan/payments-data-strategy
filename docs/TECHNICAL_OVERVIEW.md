# Technical Overview — Payments Data Strategy Demo

A discussion-ready, end-to-end technical breakdown of how this project works:
how the data is generated, how it's stored, what DuckDB and Parquet are and why
they're used, how the AI agents are built, and the methodology and design
rationale behind each choice.

Every section has two layers:
- **Plain language** — what it does and why, in everyday terms.
- **Technical** — the implementation detail you'd discuss with an engineer.

---

## 0. The one-paragraph summary

This is a **synthetic data product**. It invents a realistic universe of card
transactions for five fictional merchants in one fictional metro, then exposes
that data through a dashboard and a set of AI agents that answer business
questions — including *privacy-safe* comparisons against competitors. Nothing is
real: there are no real people, no real cards, no real stores. But the data is
*statistically* realistic, generated by an 8-stage simulation where each stage
causally feeds the next (geography → people → shopping trips → baskets →
payment → prices → events). The whole thing is **deterministic** (same seed in,
identical data out) and **config-driven** (you change behavior by editing YAML,
not code). Data is stored as **Parquet files** and queried with **DuckDB** — an
analytics-optimized combination that replaced an earlier SQLite database.

---

## 0.5 Project context & the thesis

**Plain language:** The whole demo exists to tell one story: a payments company
(Verifone) sits at the intersection of *point-of-sale* data (what's in the basket)
and *payment* data (how it was paid), across a whole installed base of merchants.
That vantage point lets it see things no single merchant can — like how your prices
or your foot traffic compare to your competitors down the street. To make that story
concrete and demoable, the project invents a small but realistic market and builds
the analytics that would run on top of it.

**Technical / design decisions:**

- **The cross-merchant thesis.** The product models Verifone observing baskets,
  payment fields, and merchant context *across* merchants — so the marquee feature
  is privacy-safe peer comparison (your dairy pricing vs the same-segment peer set,
  your neighborhood foot traffic vs the market). Everything in the data layer exists
  to make that comparison both *possible* (shared customers, comparable products)
  and *defensible* (privacy by construction).

- **Real banner names, explicitly fictional metro (D2).** The five merchants use
  *real* brand names (Kroger, Acme, Winn-Dixie, Taco Bell, TJ Maxx) because the
  names instantly convey positioning — value vs premium grocer, QSR, off-price. But
  the metro carries a **visible disclaimer** that it's fictional, and that disclaimer
  is *required*, not cosmetic: these three grocers **cannot coexist in any real US
  metro** (Kroger exited North Carolina in 2020, Acme is a Northeast/Mid-Atlantic
  banner, Winn-Dixie is Deep South). The cross-merchant thesis *needs* them sharing
  one market, so the market has to be invented. Honest framing beats a fake-realistic
  geography that an informed viewer would catch.

- **Census, not a panel (D1).** The generator models *every* transaction at the
  served merchants over the window, not a sampled panel of cards. This matters for
  defensibility: peer comparisons and anomaly detection are computed on a complete
  population, so there's no sampling-bias caveat to explain away.

- **The panel.** Five merchants across three segments in one ~Charlotte-modeled
  metro: three grocers (Kroger / Acme / Winn-Dixie, 5 stores each), one QSR (Taco
  Bell, 9 stores), one off-price retailer (TJ Maxx, 5 stores) — 29 stores in 8
  zones. ~100k cards shop across them with deliberate ~32% multi-merchant overlap
  (~6% all-three), over a 90-day window (Mar 1 → May 29, 2026). This specific shape
  is what makes the analytics interesting: shared customers enable cross-merchant
  questions; the two grocers-per-grocer peer structure is what the lake's privacy
  floor is tuned around (§4.2).

## 1. Language and stack

**Plain language:** It's a Python project. The data is stored as files on disk
(not a traditional database server). The AI features call Anthropic's Claude
models. The dashboard is a lightweight Python web app.

**Technical:**

| Concern | Choice |
|---|---|
| Language | Python 3.11 |
| Package/dependency manager | `uv` |
| Numerical / data work | `numpy`, `pandas` |
| Storage format | **Parquet** (columnar files) |
| Query engine | **DuckDB** (in-process analytical SQL) |
| Parquet writer | `pyarrow`, **pinned to 17.0.0** for byte-stable output |
| Config | YAML (`pyyaml`) |
| AI agents | **Anthropic SDK** (Claude models) |
| Dashboard | Streamlit + Folium (maps) + Plotly (figures) |
| Tests | `pytest` |

A key architectural fact: there is **no database server**. Data lives as Parquet
files in `data/`. DuckDB is a *library* loaded inside the Python process that
reads those files directly. This is "files + an embedded query engine," not
"an app talking to Postgres."

## 2. How the data is generated

### 2.0 The generation thesis: "latent-first, observable-derived" (D11)

**Plain language:** This is the single most important idea in the whole data layer,
and it's worth getting right for the engineering conversation. The generator first
invents *hidden* truths about each shopper — how affluent they are, how loyal, what
"mission" they're on this trip — and then *derives* the things you can actually
observe (which store, what's in the basket, how they paid, what price they saw) **from
those hidden truths**. It never just rolls dice on the observable fields directly.
That ordering is what makes the data feel real: affluent neighborhoods *end up*
buying premium items and paying with credit not because a rule says "zone 5 = credit,"
but because wealthy *people* live there and wealthy people lean credit — the
correlation *emerges*.

**Technical:** D11 names the principle **latent-first, observable-derived**. Each of
the 8 layers builds *latent state* (geography → population intensity → durable
customer state → trip intent) and lower layers *derive observables* from it. A few
consequences an engineer will care about:

- **Correlations are causal, not painted on.** Payment mix isn't drawn per segment;
  entry-mode is *emergent* from the customer's wallet enrollment and the segment's
  baseline (D18.1). Banner debit-share differences fall out of the affluence mix of
  each banner's customers, not a per-banner knob. This is why the data survives an
  analyst poking at it from multiple angles.

- **It makes the validation principle meaningful.** A recurring project rule is
  "derive X from observable Y, then validate against the planted X." Because
  observables are *derived* from latents (and the latent "answer" is kept out of the
  observable surface), a downstream check that recovers, say, a customer's likely zone
  from their purchase pattern is doing real inference — not reading back the planted
  label. The lake's "observable invariant" (§4) is the same idea enforced in code.

- **No PII, ever.** At no layer are there names, emails, or raw card numbers.
  `card_id` is a 16-hex SHA-256 hash. The latent state (affluence, loyalty) is a
  modeling device, not a stored identity.

**Config-driven & segment-agnostic (D12).** The engine has *no hard-coded knowledge*
of "grocery" vs "QSR" — all behavior comes from YAML (§2.3). `config/loader.py`
enforces **7 invariants before any data is generated** (residential weights sum to
1.0, every merchant's segment resolves, zone placement references real zones, store
counts reconcile, total stores match the expected count, volume targets exist, the
affinity matrix is well-formed). The payoff: adding a 6th merchant or a new segment
is a config change the loader will validate, and a misconfigured world fails fast
instead of silently producing subtly-wrong data.

### 2.1 The big idea: a causal simulation

**Plain language:** Rather than randomly sprinkling numbers into a table, the
generator builds a believable world *in order*. First it places stores on a map.
Then it creates ~100,000 shoppers and decides where they live and how affluent
they are. Then it sends them on shopping trips. Then it fills their baskets. Then
it decides how they paid and what prices they saw. Each step depends on the steps
before it — so the data has *real internal structure*, the kind a data analyst
would actually find (affluent neighborhoods buying premium items, people shopping
at the closest store, pasta and pasta-sauce being bought together).

**Technical:** The engine (`src/generate/engine/`) is an **8-layer causal
pipeline** (one module per layer), defined by project decision **D11**. Each
layer reads the layers above it and emits a pandas DataFrame:

```
1. geography.py   →  place 29 stores across 8 zones (with map coordinates)
2. population.py  →  ~100k cards: who's active in which segments, how often
3. customers.py   →  per-card durable state: home zone, affluence, loyalty, tender
4. trips.py       →  WHEN each trip happens + WHICH store (gravity model)
5. baskets.py     →  WHAT's in the basket (mission + affinity + staples)
6. payment.py     →  HOW they paid (entry mode, wallet, connectivity)
7. pricing.py     →  the realized price per line (anchor × modifiers)
8. events.py      →  promotions + planted anomalies (with a hidden answer key)
```

`engine/run_all.py` chains these together and writes the final Parquet tables.

### 2.2 Layer-by-layer, with the methodology

**Layer 1 — Geography.** Builds 8 zones (modeled on Charlotte, NC neighborhoods)
and places 29 stores. Each zone has an `affluence` score (~0.75 to ~1.45),
residential weight, density, and a lat/long centroid. Stores are jittered around
their zone centroid. *Why it matters:* affluence and location set up everything
downstream — pricing, basket composition, and which store a shopper picks.

**Layer 2 — Population.** Generates ~100k card "profiles." Each card is assigned
a **participation archetype** (grocery-only, qsr-only, grocery+qsr, all-three,
etc.) and an **intensity tier** (core/regular/occasional) that sets how many
trips it takes. *Methodology:* per-tier trip budgets are drawn from a
**triangular distribution** whose mode equals the target mean, so the population
average lands where the spec wants it. The deliberate cross-segment overlap
(~32% of cards shop multiple merchants, ~6% all three) is what makes
cross-merchant analysis possible.

> **Plain language:** This is the step that decides "how many shoppers, how
> loyal, how busy." It's tuned so the totals match a target (~1.67M transactions
> at full scale).

**Layer 3 — Customers.** Gives each card *durable* attributes: `home_zone`
(drawn from residential weights), `affluence` (a Gaussian *around* the zone's
affluence so there's within-neighborhood spread), `loyalty_type` (grocers only),
`primary_banner`, and payment identity (credit vs debit, card network, wallet
enrollment). *Methodology of note:* credit-vs-debit propensity is a **logistic
function of affluence** — wealthier cards skew to credit — anchored to real-world
(Fed 2025 Diary) payment-mix numbers. Crucially, tender is *not* a per-merchant
knob; it emerges from customer wealth, which is the realistic causal direction.

**Layer 4 — Trips (the gravity model).** This is the most statistically
interesting layer. It decides, for each trip, *when* it happens and *which store*
the shopper visits.

- **When:** day-of-week weights (grocery skews to weekends; QSR peaks Fri–Sat;
  late-night for Taco Bell), a **pay-cycle overlay** (spending bumps early-month
  and mid-month around paydays), and hour-of-day "daypart" curves.
- **Which store — the gravity model:** the probability a shopper in zone *z*
  chooses store *s* is

  ```
  P(store s | zone z)  ∝  A_s / (distance + d₀)^β
  ```

  where `distance` is the map distance between the shopper's zone and the store,
  `d₀` (= 0.5) is a small offset preventing division-by-zero for same-zone
  stores, and `β` is a **distance-decay exponent** set *per segment*
  (grocery ≈ 2.0, QSR ≈ 2.2, off-price ≈ 1.3). A higher β means "people strongly
  prefer the nearest store." For grocery, store *brand* choice combines this
  gravity pull with the card's loyalty profile.

> **Plain language:** The "gravity model" is the well-known retail idea that a
> store pulls customers like gravity pulls objects — bigger/closer stores pull
> harder, and the pull falls off with distance. β controls how fast it falls off.
> This is why shoppers in the data mostly visit nearby stores, exactly like real
> life.

**Layer 5 — Baskets (missions + affinity).** Decides what's actually in each
basket.

- **Mission:** every trip has a "mission" (e.g. grocery *weekly_stockup*,
  *meal_tonight*, *snacks_beverages*; QSR *combo_meal*; off-price
  *apparel_refresh*). The mission sets a category distribution and a basket-size
  range (drawn triangularly).
- **Staples:** each card has a few deterministic "always-buys" SKUs, giving
  realistic repeat-purchase behavior.
- **Affinity matrix:** a config-driven set of "these go together" boosts. When an
  anchor product is in the basket, its partner's selection weight is multiplied.
  Examples (from `config/segments/grocery.yaml`):

  ```
  PASTA → SAUCE  ×5.0
  CHIPS → SALSA  ×3.0
  MILK  → CEREAL ×4.0
  BREAD → BUTTER ×2.0
  DIAPERS → WIPES ×3.0
  ```

> **Plain language:** "Affinity" = market-basket correlation. It's why someone
> buying pasta is far more likely to also buy sauce in this data — a pattern a
> real analyst would expect to find, planted here on purpose so the analytics can
> surface it.

**Layer 6 — Payment.** Per trip, derives `entry_mode` (contactless/chip/swipe/
manual), `wallet_at_tap` (Apple/Google Pay), and `connectivity_type`
(wifi/ethernet/cellular). These start from per-segment baselines and shift based
on the customer's wallet enrollment (wallet-enrolled cards skew more contactless).
QSR has more cellular connectivity (drive-thru terminals).

**Layer 7 — Pricing.** The realized price of each line item is a **chain of
multipliers** applied to the catalog's `base_price`:

```
unit_price = base_price
           × per-merchant category multiplier   (banner positioning: value vs premium)
           × private-label factor                (store brands are cheaper)
           × per-SKU competitive index           (±5%, deterministic per SKU)
           × zone effect                          (affluent zones priced higher)
           × time drift                           (~1.5% inflation ramp over 90 days)
           × line noise                           (±0.5%)
           − promo discount                       (if on promotion that day)
```

*Methodology of note:* "Known Value Items" (milk, eggs, bread — things shoppers
price-check) have their banner spread *dampened*, while specialty items get it
*amplified*. This reproduces the real retail pattern where **no single grocer is
cheapest on everything** — the cheapest banner flips by category, which is a
realistic and analytically interesting signal.

**Layer 8 — Events and anomalies.** Two jobs:
1. **Promotions:** weekly grocery ads, QSR limited-time offers, off-price
   clearance cycles — each lifts demand (a promo at 20%-off roughly doubles unit
   demand for that SKU) and applies a discount.
2. **Planted anomalies (with a hidden answer key):** deliberate, detectable
   business events:
   - **A1 — localized demand decline:** trips drop in two working-class zones
     from mid-April on, hitting the value banner (Winn-Dixie, ~40% drop) hardest.
   - **A2 — category spike:** a 3× surge in PRODUCE/FRUIT at one Kroger store in
     a gentrifying neighborhood over a few days.
   - **A3 — competitive share shift:** three grocers run pasta promos in
     overlapping weeks with *different outcomes* (one wins, one flops).

   The exact definition of every anomaly is written to a **separate answer-key
   file** the analytics layer can never see (more on this in §6).

> **Plain language:** The anomalies are like deliberately hiding specific
> "stories" in the data — a sales dip here, a spike there — so you can later test
> whether the dashboard and AI agents actually *find* them. The catch: the answer
> key is kept in a locked drawer, so the AI has to discover the story from the
> raw data, not read the answer.

#### Why each layer is *realistic* — the anchors (D13–D20)

Every modeling choice is anchored to a real-world pattern, not invented for
convenience. This is the table to have open when an engineer asks "but is any of
this actually plausible?"

| Layer | Modeling choice | Real-world anchor / rationale |
|---|---|---|
| Geography (D13) | Gravity store choice, β per segment (grocery ≈2.0, QSR ≈2.2, off-price ≈1.3) | Standard retail gravity: shoppers favor nearer stores; QSR is most local, off-price worth a longer trip |
| Population (D14) | ~32% multi-merchant / ~6% all-three overlap | Real co-shopping — loyalty is concentrated but not absolute; the overlap is the lever for cross-merchant analytics |
| Customers (D16) | Credit-vs-debit as a logistic of affluence; one card token per customer | Fed 2025 Diary payment mix; tender follows *wealth*, not a per-merchant rule |
| Trips (D15) | Weekend skew, pay-cycle lift, Taco Bell late-night | Grocery leisure-shops weekends; salary cycles drive early/mid-month bumps; QSR has a real 9pm+ surge (~4% industry → modeled higher to be detectable) |
| Baskets (D17) | Affinity must be *discoverable*, not derivable from marginals | A recommendation engine should be able to *find* PASTA→SAUCE from the data — so it's planted above what category base-rates alone would predict |
| Baskets (D17.4) | Heavy-tail basket sizes (top 20% ≈ half the units) | Pareto purchasing — a minority of big baskets drives most volume |
| Payment (D18.1) | Entry-mode *emergent* from wallet enrollment + segment | Avoids the "painted-on" correlation; banner debit differences fall out of customer mix |
| Pricing (D19.2) | Per-merchant strategy, KVI-tight / specialty-wide spread; "the SKU-level insight engine" | Rational arbitrage keeps milk/eggs close across banners; brands have pricing power in specialty — so *no banner is cheapest on everything* |
| Events (D20) | Promo lift scaled to depth; A1–A3 as the agent's answer key | Real promo calendars; anomalies are operational business events (a localized decline, a category spike, a promo win/flop) with recorded ground truth |

### 2.3 The parameters: config-driven design (D12)

**Plain language:** The "rules of the world" live in editable settings files
(YAML), not buried in code. Want a sixth merchant or a new affinity rule? Edit a
config file — you don't touch the engine. This makes the system flexible and
keeps the behavior auditable in one place.

**Technical:** Configuration lives in `src/generate/config/`:

- `global.yaml` — the master knobs: `seed: 42`, the 90-day window
  (2026-03-01 → 2026-05-29), per-segment volume targets (~1.08M grocery, ~365k
  QSR, ~225k off-price), `target_cards: 100000`, the gravity `distance_decay_d0`,
  expected store count.
- `metro.yaml` — the 8 zones (affluence, density, residential weight, centroids).
- `segments/{grocery,qsr,off_price}.yaml` — per-segment archetype: the
  distance-decay β, the affinity matrix, catalog model.
- `merchants/{kroger,acme,winn_dixie,taco_bell,tj_maxx}.yaml` — banner name,
  code, segment, positioning tier, store count, zone placement bias.

`config/loader.py` enforces **invariants before any data is generated** — e.g.
residential weights sum to 1.0, every merchant's segment resolves, store counts
reconcile with placement, volume targets exist. If the config is internally
inconsistent, it fails fast rather than producing subtly wrong data. The engine
itself is **segment-agnostic**: it has no hard-coded knowledge of "grocery" vs
"QSR" — that all comes from config.

### 2.4 Determinism: same seed, identical data

**Plain language:** Run the generator twice and you get *exactly* the same data,
down to the byte. This is essential for a demo and for testing — results are
reproducible and any change is attributable.

**Technical:** All randomness flows from one master `seed` (42), threaded into
**per-layer derived seeds** (`seed+10`, `seed+20`, …) so layers are independent
but reproducible. There are no loose `np.random.*` calls — every layer gets its
own seeded `numpy` generator. Iteration happens in sorted config order. Combined
with the deterministic Parquet writer (§3.2), two runs at the same seed produce
**byte-identical files** — verified by acceptance test **T18**.

## 3. How the data is stored: Parquet + DuckDB

### 3.1 What Parquet is

**Plain language:** Parquet is a file format for tables — think of it as a
spreadsheet saved to disk, but optimized for analytics. Its trick is that it
stores data **by column instead of by row**. If you only care about 3 columns out
of 30, it reads just those 3 off disk. It's also compressed and remembers the
data types. This makes "scan millions of rows and compute an average" extremely
fast.

**Technical:** Parquet is a **columnar, compressed, typed** on-disk format. In
this project the engine builds rows in pandas/numpy and writes them through
`src/storage/duckdb_io.py`:
- `write_parquet(df, path, sort_keys=...)` — one file.
- `write_partitioned_parquet(...)` — Hive-style `col=value/` directories.

Output tables land in `data/raw/` (the tenant census: merchants, zones, stores,
customers, products, transactions, transaction_items, promotions) and `data/eval/`
(the anomaly answer key only).

### 3.2 Deterministic writes

The writer is tuned so the *bytes* are reproducible: `pyarrow` pinned to 17.0.0,
single-threaded writes, columns sorted alphabetically, explicit `sort_keys` to
fix row order, zstd compression at a fixed level, fixed row-group size, and **no
run timestamps** in the metadata. Same input → same file. This is what makes the
determinism guarantee (T18) hold at the storage layer.

### 3.3 What DuckDB is and why it's used

**Plain language:** DuckDB is a database engine that runs *inside* your program —
no server to install or connect to. People call it "SQLite for analytics." It
reads Parquet files directly and is built to crunch big aggregate queries
(sums, averages, group-bys over millions of rows) very fast.

**Technical:** DuckDB is an **embedded, in-process, columnar OLAP** engine. In
this project it is the **read/query engine and is read-only at runtime** — it
never writes the dataset (Parquet is the written artifact). `read_parquet` returns
a **lazy DuckDB relation, not a DataFrame**: DuckDB pushes filters and
projections down into the Parquet reader, so you aggregate over millions of rows
in SQL and only materialize a small final result to pandas. The dashboard opens
an **in-memory DuckDB connection** and exposes the Parquet files as SQL views.

### 3.4 Why this differs from the old SQLite implementation

**Plain language:** The previous version (v3) stored everything in a single
SQLite database file that the program both wrote to and read from. v4 switched to
"immutable Parquet files + DuckDB as a fast reader." The new approach is faster
for the heavy analytical queries this demo runs, reproducible byte-for-byte, and
cleaner about keeping the answer key out of reach. The SQL barely changed because
the dashboard wraps the new files in views that mimic the old column names.

**Technical (decision D3):**

| | v3 SQLite | v4 DuckDB + Parquet |
|---|---|---|
| Storage | one mutable `payments.db` row-store | immutable columnar Parquet files |
| Engine role | read **and** write the DB | DuckDB read-only; Parquet is the artifact |
| Query style | row-oriented (OLTP-style) | columnar scans (OLAP) |
| Big aggregate scans | slower | fast — reads only needed columns |
| Determinism | hard to guarantee identical files | byte-identical by construction (T18) |
| Answer-key safety | one file holds everything | physical dir split: census vs answer key |

Practical migration notes: `data.py::_conn()` now returns an in-memory DuckDB
connection; the v4 Parquet is exposed as **aliasing views** that bridge old query
vocabulary onto new column names (e.g. `banner_code AS merchant_id`,
`subtotal AS txn_total`), so most dashboard SQL was unchanged. Dialect shifts came
with the move (`EXTRACT(hour FROM …)` instead of `SUBSTR`, `date_trunc('week', …)`
for week bucketing, strict GROUP BY). The v3 demo is preserved at git tag
`v3-final`.

### 3.5 Why DuckDB+Parquet was the right call — the full rationale (D3, D4)

**Plain language:** The switch wasn't aesthetic — the old SQLite setup was
genuinely buckling. SQLite stores data row-by-row, and the old design built a
*separate copy of the competitor "lake" for each of the five merchants*. That
combination ballooned the database to **2.7 GB at only ~235k transactions** — and the
target is *seven times* that volume. It would not have fit on a laptop. DuckDB +
Parquet fixed both problems at once: columnar Parquet is 5–10× smaller, and DuckDB
reads it fast without copying anything.

**Technical (D3 + D4):**

- **The SQLite pain points (D3).** SQLite is a fine *row-oriented OLTP* engine, but
  this workload is *OLAP* — wide aggregate scans. Two concrete failures drove the
  change: (1) row storage is bulky and uncompressed, and (2) the v3 lake was
  **materialized 5× — once per viewer** — so the file hit **2.7 GB at 235k txns**.
  At the ~1.67M-txn target that's untenable.

- **Why DuckDB + Parquet specifically.** DuckDB keeps SQLite's best property — it's
  **in-process, zero-server, single-file-simple** — but is built as a **columnar OLAP
  engine** for exactly the group-bys and aggregations this demo runs. Parquet is
  **columnar + compressed (5–10× smaller)** and handles tens of millions of rows on a
  laptop. Crucially, it's also **closer to a real production architecture** (a
  columnar data lake queried by an analytical engine), which strengthens the
  executive narrative — the demo's storage story mirrors how this would actually be
  built.

- **D4 — single lake, query-time viewer scoping (kills the 5× blow-up).** Rather than
  materialize a physical lake per viewer, the design moved to *one* surface scoped at
  query time. (Note: the *current* line-item lake of §4 does materialize a small
  per-viewer pair for clean isolation, but the data is tiny and identity-stripped —
  the 5×-full-database explosion that D4 targeted is gone.)

- **The tradeoff accepted.** DuckDB-on-Parquet is **read-optimized and effectively
  immutable** — you don't do row-by-row updates the way you might in SQLite/Postgres.
  For this product that's not a loss; the dataset is *generated once and queried many
  times*, which is the exact shape columnar storage is built for. There's no
  transactional write path to give up because there was never one to begin with.

> **One-liner for the discussion:** "We moved from a row-store that hit 2.7 GB at a
> seventh of target volume, to a columnar lake an embedded OLAP engine reads
> directly — smaller, faster on the aggregate scans we actually run, byte-reproducible,
> and shaped like the production architecture it's demoing."

## 4. The peer "lake" — privacy-safe competitor comparison

**Plain language:** A big selling point of the demo is letting a merchant compare
itself to its *competitors* — but you obviously can't show one merchant another's
raw data. The "lake" is a carefully sanitized copy of everyone *else's* data,
built separately for each merchant, with all identifying details stripped and a
rule that you can only ask *aggregate* questions (averages, totals) about groups
of at least 5 — never about an individual transaction.

**Technical:** The peer surface is a **raw line-item lake**, built by
`src/lake/build_line_items.py` into `data/lake/items/<VIEWER>/` (one
`lake_transactions` + `lake_stores` pair per viewing merchant). Its privacy model
is layered:

1. **Viewer exclusion (structural):** the viewer's own rows are *deleted* before
   the file is written. Their identity never exists in the published frame — it's
   not a runtime filter that could be bypassed.
2. **Identity reduction:** no merchant names, no customer linkage. IDs are
   replaced with non-reversible SHA-256 tokens; timestamps are coarsened to
   hour-buckets; the only published geography is a `neighborhood` label.
3. **Relative labeling:** each peer row is labeled `peer` (same segment as the
   viewer) or `merchant` (different segment) — so the same store is a "peer" to
   Kroger but a "merchant" to TJ Maxx, all without naming the competitor.
4. **Read guard (`observable_guard.py`):** the builder may only read *observable*
   columns. Planted "answer" columns (a customer's true `home_zone`,
   `loyalty_type`; a store's `zone_id`) are **forbidden** — this stops the subtle
   failure mode of reading a planted label and relabeling it "derived."
5. **Query-time k-anonymity (`lake_sql.py`):** every peer query is parsed into
   DuckDB's own AST and forced to be a **single aggregating SELECT** (no
   `SELECT *`, no raw rows). A `COUNT(*)` is injected; any group backed by **fewer
   than 5 line items (k=5) is suppressed**, and the number of suppressed groups is
   surfaced for transparency. Only `lake_transactions`/`lake_stores` are readable
   — `read_parquet`-style reach-arounds to the raw census are rejected.

Tenant isolation on a merchant's *own* data is enforced separately by
`isolation.py` (a viewer predicate + CTE-wrap, so a query can't reference another
merchant).

### 4.1 How the peer lake is actually built

**Plain language:** The lake is built once, offline, by a script (`make
lake-items`). Think of it as a privacy "darkroom" that takes the full raw dataset
and develops five separate, redacted copies — one for each merchant to look at,
each showing only *everyone else's* data with all the identifying marks blacked
out. The build happens in two stages: first it assembles one big internal table of
every purchase line in the whole panel (with the labels still attached, in memory
only — never saved), then for each merchant it makes a redacted cut: delete that
merchant's own rows, relabel the rest as "peer" or "other-industry," black out the
names and IDs, and save just that.

**Technical:** the builder is `src/lake/build_line_items.py`, run via
`scripts/build_line_items.py` / `make lake-items`. It writes
`data/lake/items/<VIEWER>/{lake_transactions,lake_stores}.parquet` plus a
`metadata.json`. Two functions do the work:

**Stage 1 — `build_global_lines()`: one enriched, generalized, tokenized frame for
the whole panel (kept in memory, never written).**

1. **Read only observable columns.** It pulls three tables *exclusively* through
   `observable_guard.load_table` — `transaction_items` (line fields),
   `transactions` (store, banner, timestamp, payment fields), and `stores`
   (`neighborhood` only). The guard forbids planted/answer columns: it never reads
   `customers`, `zones`, or a store's `zone_id`. This is the §1 "observable
   invariant" — the lake is built from what a payment processor could actually
   observe, not from the generator's hidden ground truth.
2. **Join in DuckDB.** The three frames are registered and joined with one SQL
   statement (columnar, low peak memory), producing one row per purchase line.
3. **Generalize during the join:**
   - timestamp → `txn_date` (date only, no time-of-day) **plus** `hour_bucket`
     (`EXTRACT(hour) * 10 / 24` → a coarse 0–9 bucket). Exact transaction time is
     destroyed; only a coarse time-of-day band survives.
   - payment columns renamed to stable lake names (`tender → payment_type`,
     `network → card_network`); `wallet_at_tap` collapsed to a `wallet_type` of
     the provider or `'none'`.
   - the only geography kept is the real `neighborhood` string (no ZIP, no
     lat/long, no zone code).
4. **Tokenize identifiers (non-reversible).** `txn_id` and `store_id` are replaced
   with **salted SHA-256 tokens** truncated to 16 hex chars. The salt is
   `f"lake_v35:{seed}"` — derived from the generation seed, so it's *deterministic*
   (reproducible builds) but not guessable. Efficiency detail: tokens are computed
   over the **unique** id values (~1.66M txn ids) and mapped back, not hashed
   per-line (~10.76M lines). The line id is just `token + "-" + sequence` — already
   non-reversible, avoiding 10.76M fresh hashes.

   Critically, this frame still carries the real `banner_code` — because the next
   stage needs it to slice and label per viewer — which is exactly why **this frame
   is never written to disk**.

**Stage 2 — `scope_lines_for_viewer(global_lines, viewer)`: the per-merchant
redacted cut (done five times).**

1. **Viewer exclusion (structural).** `peers = global_lines[banner_code != viewer]`
   — the viewing merchant's own rows are physically *removed from the frame* before
   anything is published. This is the strongest guarantee: it's not a `WHERE` clause
   applied at query time that could be bypassed; the viewer's data simply isn't in
   the file.
2. **Relative relabeling.** Each surviving row is tagged `peer` (same segment as the
   viewer) or `merchant` (different segment) — computed *relative to this viewer*.
   The same Acme store is a `peer` in Kroger's lake but a `merchant` in TJ Maxx's
   lake. There are **no per-competitor identities** (the old `peer_a`/`peer_b`
   pseudonyms are gone) — you can benchmark against "the peer set," not against a
   named rival.
3. **Identity strip via projection.** The published frame is projected down to a
   fixed allow-list of columns (`_TXN_PUBLISHED`): the tokens, generalized
   date/hour, `peer_relationship`, category/subcategory, and the raw analytical
   fields (`unit_price`, `qty`, `discount`, `line_total`, payment dims). The real
   `banner_code`, `store_id`, `txn_id`, and `line_id` never appear in the output.
4. **Store reference.** A deduplicated `lake_stores` table (one row per peer store:
   tokenized id, `peer_relationship`, `peer_segment`, `neighborhood`) is emitted for
   neighborhood joins.

**Stage 3 — write + metadata.** Each pair is written with the deterministic
`write_parquet` (sorted, byte-stable), and `metadata.json` records each viewer's
segment and **how many other merchants share it** (`segment_peer_count`). That count
is what the specialists branch on *structurally* — e.g. Taco Bell and TJ Maxx have
**zero** same-segment peers, so their agents answer own-data-only instead of
fabricating a peer comparison.

> **Note on the raw analytical fields:** prices, quantities, and categories pass
> through **un-coarsened**. The privacy protection on them is *not* blurring the
> values — it's the **k=5 query-time floor** (§4, `lake_sql.py`): you can compute
> any aggregate you like, but only over groups of ≥5 line items. This keeps the
> data analytically useful (real dollars, real comparisons) while making
> individual-level inference impossible.

> **Why this is the right design:** It enforces privacy *by construction* at
> multiple independent layers (physical separation, identity stripping,
> aggregation-only, k-anonymity) rather than trusting any single check or trusting
> the AI to behave. Even a maliciously-crafted query can't return an individual's
> data or another merchant's identity. And because the build is deterministic
> (seed-derived salt), the redacted lake is reproducible and auditable — you can
> rebuild it and get byte-identical files.

### 4.2 Why these privacy choices — the tradeoffs (and what was rejected)

This is the section to read before defending the privacy design to an engineer,
because the choices are *deliberately minimal* and the project is honest about that.

**The evolution: aggregates → line items.** The earlier design (Wave 2) published
**pre-computed aggregate tables** at fixed dimensional grains, in *unitless indices*,
reachable only through a filter-only tool. It was *more* privacy-conservative on
paper — but it failed in practice:

- The agent could only *consume* a **closed dimensional vocabulary it didn't design**
  — it couldn't compose its own view. Compensating for that one upstream choice took
  **sixteen structural fixes** downstream.
- Pricing came out **direction-only**: "you're above an index of ~1.0," never the
  actionable "your dairy is $3.50 vs peer $3.42."
- A pile of residual bugs (flat demand indices, label-space mismatches, unstable
  merges) all traced to the aggregate-table lock-in — *not* to the agents.

The current line-item lake **removes that root cause**: peer data is raw line items
the agent queries with SQL — *the same motion it already uses on its own data*. A
cross-merchant comparison becomes the native "query own, query peer, compare," with
no merge tool, no grain-matching, no index transform — and **the result table itself
is the evidence**. (This is a recurring project pattern: when symptoms plateau after
many patches, re-architect rather than patch again.)

**Why k=5, and not something stronger.** The privacy floor is `k=5` — aggregates must
cover ≥5 underlying line records. The reasoning is structural to *this* dataset:

| Alternative | Why it was rejected here |
|---|---|
| **k≥50** (a stricter floor) | Each grocer has only **2 same-segment peers** (2 stores each). A k≥50 floor would suppress nearly every 2-store category slice — the comparison would return almost nothing. k=5 lets thin-but-real peer comparisons through. |
| **Differential privacy (noise)** | DP injects mathematical noise into the numbers. On *synthetic* data where no real merchant is exposed, that trades away the analytical fidelity (real dollars) that's the whole point — for protection against a re-identification risk that doesn't exist at demo scale. |
| **l-diversity** | Impractical with only 2 peers — the attribute values are homogeneous anyway, so l-diversity has nothing to diversify over. |

k=5 is also a **single configurable constant** — production can raise it without a
code change. And it's enforced at **query time** (not baked in at build), so the agent
can *retry at a coarser grain* when a cell is too thin, rather than hitting a
permanently-suppressed value.

**Why parse the SQL, not regex it.** The "aggregating-only" rule is enforced on
**DuckDB's own parsed AST** (`json_serialize_sql`), not a regex. Regex genuinely
*cannot* reliably tell an aggregating query from a raw-row select once CTEs, joins,
and subqueries are involved — so a regex guard would be security theater. Parsing the
AST makes raw-row exposure **structurally impossible**, with the k=5 count-floor as a
second line of defense.

**The honest residuals (flagged, not hidden).** At the demo's minimal posture, two
small exposures are knowingly accepted and earmarked for production tightening:
`MIN`/`MAX` on raw value columns are still allowed (a single-value peek), and
`GROUP BY lake_txn_id` can produce per-basket aggregates for ≥5-line baskets (still
unlinkable, anonymous transactions). Neither leaks identity; both are on the
"tighten for production" list.

**The stated posture.** The project is explicit (D21): this is a **deliberately
minimal demonstrator posture on synthetic data**; the **production target** adds
**k≥50 and differential-privacy-noised aggregates**. Saying that plainly is part of
the design — it's a credibility move, not a gap to paper over.

## 5. How the AI agents are built

### 5.1 The mental model

**Plain language:** When you ask a business question in the dashboard, the system
routes it to one of several specialist "analysts" (each an AI agent with a focus —
pricing, demand, trade area, anomalies — plus a general "Advisor"). The agent
doesn't make up numbers. It *writes SQL queries*, runs them against the real data,
looks at the results, and then writes a short answer where **every number is
checked against the query results** before you see it.

**Technical:** Agents live in `src/agents/`. The architecture:

- **Routing:** a free-form question goes through an **orchestrator** that uses a
  fast model (Claude Haiku) to classify it to one of five agents
  (`pricing`, `demand`, `trade`, `anomaly`, `advisor`), with **keyword-based
  fallback** if the model call fails. Dashboard "pill" questions skip routing
  because their agent is already known.
- **Five agents:** four domain specialists + an **Advisor** (general/multi-topic
  fallback). All subclass a shared `Specialist`.
- **Model:** specialists default to Claude Haiku 4.5 (cheap, fast), with an env
  var to swap in Sonnet for quality testing. Per-call telemetry tracks tokens and
  cost.

### 5.1a How the orchestrator works — is it "just Haiku reading and assigning"?

**Plain language:** Yes — at heart it's a single, cheap classification step. When
you type a free-form question, a fast Claude model (Haiku) reads it together with a
short description of who you are (which merchant) and what the five specialists do,
then replies with a tiny machine-readable verdict like *"send this to pricing."*
That's the whole job. The router does **no data work** — it never touches the
database, never does math, never writes the answer. It's a switchboard operator: it
listens to the request and connects you to the right desk. The chosen specialist
does all the real work afterward. There are also two important safety nets so the
switchboard never jams (below).

**Technical:** the router (`src/agents/orchestrator.py::route`) is a **single,
non-agentic LLM call** — not a tool loop, not the multi-turn machinery the
specialists use. The mechanics:

1. **Prompt assembly.** A system prompt (`prompts/orchestrator.md`) is rendered with
   the viewer's identity (`{{viewer_id}}`, `{{viewer_name}}`, `{{viewer_segment}}`)
   so routing can be merchant-aware. The user's question is the only user-turn
   content.
2. **One Haiku call.** `client.messages.create(model=MODEL_ROUTER, …,
   max_tokens=200)` — pinned to Haiku (`claude-haiku-4-5-20251001`) **even when the
   specialists are running Sonnet**, because routing is a cheap classification, not
   reasoning. No tools are passed; the model just emits text.
3. **Structured parse.** The model is asked to return JSON like
   `{"primary": "pricing", "rationale": "..."}`. `_parse_router_output` regex-extracts
   the first `{...}` and validates `primary` is one of the five
   `VALID_AGENTS`. If parsing fails or the agent name is invalid → fall through to
   the keyword fallback.
4. **Dispatch.** The returned `RoutingDecision` (primary agent + rationale +
   `via_fallback` flag + router token/cost telemetry) is handed to
   `build_agent(agent_id, ctx)` — a plain factory that instantiates the chosen
   `Specialist` subclass. `Orchestrator.ask` then calls `agent.answer(question)`.

So the *only* thing the model decides is **which of five labels**. Everything that
produces numbers happens in the specialist's own tool loop (§5.2).

**The two safety nets** (why it's more robust than "just Haiku"):

- **Keyword fallback (`_keyword_route`).** If Claude is unavailable
  (`L.is_available()` is false — e.g. no API key), or the call throws, or the
  output won't parse, routing falls back to a **deterministic keyword table**
  (`_KEYWORD_RULES`). Each agent has a phrase list (e.g. *price / expensive / price
  index* → pricing; *spike / decline / why is* → anomaly; *neighborhood /
  expansion / cohort* → trade; *payment / contactless / wallet* → advisor). First
  match wins, and the order is deliberate — payment-ish phrasing is checked before
  pricing so "contactless vs peers" goes to the Advisor, not Pricing.
- **Advisor as the no-match target.** If *no* keyword matches, the question routes
  to the **Advisor** (the general specialist), never to an error. This replaced v3's
  behavior of force-routing unknowns to a segment-default specialist. The router is
  wrapped so it **can never fail** — worst case you get a sensible generalist.

**Why this design is right:** routing is a classification problem, so it gets the
cheapest capable model and a single call (latency + cost minimized). Keeping the
router free of tools and data access means a routing mistake can only send you to a
slightly-less-ideal specialist — it can't produce a wrong *number*, because the
router never computes one. And the deterministic fallback means the product still
works with no API key at all (it just routes by keywords). It is "Haiku reading and
assigning," but with a deterministic backstop and a guaranteed safe default.

### 5.2 The agentic loop and the four tools

**Plain language:** The agent works in a loop: "look at the data schema → write a
query for my own data → write a query for the peer data → compare → write the
answer." It has exactly four tools it's allowed to use, and the final answer is
itself a tool call with a strict structure (headline, evidence, takeaway).

**Technical:** The specialist runs a bounded **tool-use loop** (capped turns + a
wall-clock ceiling). Each turn calls the model with four tools available:

1. **`schema_info`** — returns the table/column schema (introspected from Parquet
   at runtime) so the model knows what it can query.
2. **`query_tenant(sql)`** — runs viewer-scoped SQL against the merchant's own
   `data/raw/` tables. Tenant isolation is enforced before execution.
3. **`query_lake_sql(sql)`** — runs aggregating SQL against the peer lake, with
   the k=5 / aggregation-only guard from §4.
4. **`emit_response(...)`** — the *terminator*. The model must produce a
   **structured answer**: a one-sentence `headline`, 2–4 `evidence` bullets, an
   optional `so_what`, and a list of `claims` (each number tied to where it came
   from).

The methodology is **"two queries, then compare"**: fetch own data with
`query_tenant`, fetch peer data with `query_lake_sql`, and reason over both. There
is no automatic "merge" step in this version — the comparison happens in the
model's reasoning, constrained by the validator below.

### 5.3 The grounding wall: the claims validator

**Plain language:** This is the most important trust mechanism. After the agent
writes its answer, a validator re-checks **every number** in the prose against the
actual query results. If a number matches, it stays. If it's slightly off, it's
corrected to the true value. If it can't be traced to the data at all, that claim
is *removed*. This is what stops the AI from "hallucinating" a confident-but-wrong
statistic.

**Technical:** `claims.py` runs a **two-pass validator**
(`validate_structured_response`) over each field of the response:

- **Pass A (declared claims):** every number the model declared is re-resolved
  against the result frame. Within a ~1% tolerance → **passed**; close but
  imperfect → **normalized** (prose rewritten to the exact value); untraceable or
  divergent → **stripped**. It also runs *semantic* checks (e.g. a magnitude
  mislabel like "$6.4B" for a 6.4M cell, or an "up" word on a negative delta).
- **Pass B (undeclared numerics):** it scans the prose for *any* numeric token,
  classifies each as a **metric** (must trace to data — has a `%`, `$`, "index",
  "share", etc.) vs **structural** (exempt — "5 merchants", "12 weeks"), and
  strips any metric number not covered by a passing claim.

The unified output type is `AgentResponse` (`response.py`) with a structured
`headline`/`evidence`/`so_what` contract and a derived read-only `.prose`. This
"single source of truth + recompute-everything" design is the structural wall
that makes the agents *defensible*.

> **Plain language takeaway:** The AI is allowed to *phrase* the answer, but it is
> not allowed to *invent* the numbers — the numbers are mechanically verified
> against the database every time.

### 5.3a Why it's built this way — the unification principle & residuals

**The single-source-of-truth principle (D8).** The keystone decision is that **the
query result is the single source of truth** for everything the user sees. The model
never gets to introduce a number from "thinking" — every figure must resolve to a
cell in a frame the agent actually queried. That's what makes the system *defensible*
rather than just *impressive*: there is no path from "the model felt confident" to "a
number on screen." This is also why charts (when they return) will be built from the
*result columns*, never from a model-supplied value.

**Why two passes, not one.** A single "check the declared numbers" pass would miss
the sneakiest failure: a number the model *didn't* declare but slipped into the prose.
So Pass A validates what the model *claimed*, and Pass B independently scans the prose
for *any* metric number and strips anything uncovered. Together they cover the full
surface — fabrication and undeclared leakage both. The metric-vs-structural classifier
is what lets "5 stores in Zone 3 over 12 weeks" survive (those are structural counts)
while "$3.50" or "12% above peers" must trace.

**The known residuals (§15) — honest limits.** The validator checks a number's
*value*, but two *labeling* mistakes can survive because they're about wording, not
the figure itself:

| Residual | What it looks like | How it's mitigated | Durable fix (deferred) |
|---|---|---|---|
| **Magnitude/scale mislabel** | model writes "$6.4B" for a 6.4M cell | prompt Rule 4b ("match the cell's order of magnitude") | server-side scale sanity check at validation time |
| **Direction mislabel** | headline says "above peers" while the gap is actually negative | prompt Rule 4b ("read direction off the numbers") | server-side check that the comparative word matches the sign of own − peer |

These occur in **under ~5% of runs** and are mitigated reliably by prompt discipline;
the durable server-side checks are designed but deferred as non-blocking. The point
for the discussion: the *number* is always right (the validator guarantees it); the
residual risk is in the *noun or direction word* next to it — a smaller, well-scoped,
documented gap, not an open-ended hallucination risk.

### 5.4 What's deferred

Charts are currently **off** (`CHARTS_ENABLED = False`): agent answers are
explanation-only in this version. The chart builder (`chart_build.py`) and a
dormant `merge_own_and_peer` are kept as scaffolding for the next wave, when
charts become *agent-invoked* (model-driven from result columns) rather than
hard-coded.

## 6. Keeping the answer key away from the analytics

**Plain language:** The anomalies (the hidden "stories") have an answer key. To
make the demo honest, that answer key is stored in a *physically separate folder*
the AI and the lake can never read. So when an agent "finds" an anomaly, it really
did find it in the data — it didn't peek at the answer.

**Technical:** `data/raw/` (census) and `data/eval/` (`anomalies_groundtruth`
only) are separate directories. The lake builder reads `data/raw/*` exclusively,
and `isolation.py` forbids any path under `data/eval/`. "The answer key never
reaches the lake or the agents" is enforced **by construction**, not by
convention.

## 7. Testing and quality

**Plain language:** There's a substantial test suite that checks the data is
realistic (right transaction volumes, right basket correlations, the anomalies are
actually detectable), the privacy rules hold, and the AI plumbing works — all
*without* calling a live AI model (the model is faked for tests, so tests are
fast and deterministic).

**Technical:**

- **`tests/data_quality/` (T1–T18):** ~36 acceptance tests mapping to spec
  invariants — volume bands, average order value, day-of-week ratios, Taco Bell
  late-night share, cross-merchant overlap, **affinity lift** (e.g. PASTA→SAUCE),
  pricing variation (no banner cheapest on everything), promo lift, **anomaly
  detectability**, small-cell readiness for the lake (k≥5), and **T18
  reproducibility**. Each test prints its measured magnitude next to the band, and
  those magnitudes are published in `docs/DQ_REPORT.md`.
- **`tests/lake/` (L01, L02 + line-item tests):** the observable-data guard,
  tenant isolation, and the lake's privacy invariants (no identity columns,
  viewer exclusion, deterministic tokenization, k-anonymity).
- **`tests/agents/`:** specialist behavior with a **fake LLM** (`_fake_llm.py`)
  that returns scripted tool calls — so the agentic loop, tool dispatch, and
  claims validator are all tested deterministically without a network call.
- **`tests/test_engine_*.py`:** per-layer unit tests for the generation pipeline.

## 7.5 Deliberate simplifications & what's out of scope

**Plain language:** A good demo is as much about what you *leave out* as what you
build. The project made explicit choices to keep the world focused and honest, each
with a reason. Knowing these makes you look sharper in the discussion — you're not
hiding the edges, you're explaining them.

**Technical — the explicit exclusions and why:**

| Excluded | Why (the rationale) |
|---|---|
| **Fraud / chargebacks / tampering** (D20.3) | Real fraud is rare (~0.05–0.1%) and needs a separate risk model. The planted anomalies (A1–A3) simulate *operational* shocks (a supply disruption, a category surge), which is the business-analytics story this demo tells. Anomaly agents are **business-anomaly-only, never fraud**. |
| **One card per customer** | Avoids household-merging complexity. The token is *structured for extensibility* — multi-card households can be added later via config without breaking the data contract. |
| **Card-present only** | No online / mobile-ordering / gifting channels. Those need separate acquisition + fulfillment models; payments-at-the-register is the clean 80% case. |
| **No inventory / stockouts** | Every item is always available. Out-of-stocks are geography- and time-specific; modeling them is a future anomaly type, not a Wave-1 requirement. |
| **No in-window churn** | The 100k cards are stable across the 90 days — too short a window for seasonal churn to dominate. Customer-lifetime dynamics are a later wave. |
| **Promo depth ≤ 40%** | No deep loss-leaders or BOGO mechanics. Keeps elasticity modeling simple while capturing the depth-driven-lift 80% case. |
| **No l-diversity / differential privacy** (D21.3 / D24.3) | Deferred to the production posture; the demo runs the minimal k=5 layer (see §4.2). |
| **Charts in agent answers** | Removed in Wave 4; return in Wave 4.1 as *agent-invoked* helpers built from result columns (not hard-coded per question). |
| **S3 / cloud / Lambda backends** | Parquet committed locally while small; a cloud lake is a production concern, not a demo one. |

The throughline: every exclusion is a **scoping decision with a stated reason and a
re-entry path**, not an oversight. That's the honest-engineering posture the whole
project takes.

## 7.7 How the architecture got here — the evolution

**Plain language:** This system wasn't built in one shot; it went through several
rounds, and each round *re-architected* rather than patched. That's worth surfacing,
because the project's explicit method is: when you've made a dozen small fixes and the
problems keep tracing back to one upstream choice, **replace the choice** instead of
adding a thirteenth patch.

**Technical — the wave history:**

- **v2.5 / v3** — SQLite database, a Wave-2 *aggregate* peer lake (pre-computed,
  unitless indices, filter-only access), and hard-coded per-question charts. Worked,
  but each of those three became a ceiling: SQLite ballooned to 2.7 GB (§3.5), the
  aggregate lake forced 16 compensation fixes (§4.2), and the chart system was a
  patch over mismatched data shapes.
- **v4 / Wave 1** — the current generation engine: the config-driven 8-layer causal
  pipeline writing deterministic Parquet.
- **v4 / Wave 3.5** — the root-cause rewrite of the peer surface: the **line-item
  lake** queried by SQL (real dollars, native "query own / query peer / compare") and
  **structured, validated agent responses** replacing the aggregate lake + the old
  agent shapes.
- **v4 / Wave 4** — the **dashboard rebuilt on DuckDB-on-Parquet** (the SQLite
  retirement), wired to the Wave 3.5 agents, charts deferred.
- **v4 / Wave 5** — a simpler, honest **public report** describing the v4 system as it
  actually is.

Each arrow is a deliberate re-architecture aimed at a root cause — the same discipline
that produced the line-item lake (replacing aggregates) and DuckDB (replacing SQLite).
The prior versions are preserved (e.g. git tag `v3-final`) so the comparison is
honest and reversible.

## 8. Why this architecture is the right call

A talking-point summary for the engineering discussion:

1. **Causal generation over random fill.** Building data in dependency order
   (geography → people → trips → baskets → prices → events) yields *realistic
   correlations* an analyst would actually find — and it makes the data
   explainable, because every pattern traces to a modeling decision.

2. **Config-driven + segment-agnostic.** Behavior lives in YAML with validated
   invariants; the engine has no hard-coded segment knowledge. Extending the
   universe is a config change, and the config is the single auditable source of
   the "rules of the world."

3. **Determinism end-to-end.** One seed → byte-identical Parquet. Reproducible
   demos, attributable changes, and meaningful regression tests.

4. **Parquet + DuckDB over SQLite.** Columnar storage + an embedded OLAP engine is
   the right tool for "scan millions of rows and aggregate," which is exactly what
   a dashboard and analytics agents do. No server to operate; files are portable
   and immutable.

5. **Privacy by construction.** The peer lake stacks independent guarantees
   (physical separation, identity stripping, aggregation-only, k=5 anonymity, AST
   enforcement) rather than trusting any single check or the model's good behavior.

6. **Defensible AI.** The agents query real data and every number is mechanically
   re-verified against query results before display. The model controls *wording*,
   not *facts*. This is the difference between a demo that's impressive and one
   that's trustworthy.

7. **Honest evaluation.** The anomaly answer key is physically unreachable by the
   analytics layer, so "the AI found the anomaly" is a real claim.

8. **Latent-first, observable-derived (D11).** Correlations are *causal*, not painted
   on — observables are derived from hidden state, so the data holds up when an analyst
   attacks it from multiple angles, and the validation principle (derive-then-check)
   actually means something.

9. **Defensibility encoded as tests, not asserted (D10).** Every realism claim is a
   test with a measured magnitude and a band (§2.5), published in `docs/DQ_REPORT.md`
   and run in CI — the demo can *prove* its data is realistic.

10. **Honest about its own limits.** The privacy posture is stated plainly as a
    *minimal demonstrator* with a named production target (k≥50 + DP); the agent's
    residual labeling risks are documented (§5.3a); the scope exclusions each carry a
    reason (§7.5). Credibility comes from naming the edges, not hiding them.

## 9. Glossary (plain-language)

- **Synthetic data** — invented but statistically realistic data; no real people
  or transactions.
- **Parquet** — a columnar, compressed file format for tables; fast for analytics.
- **DuckDB** — an analytics database engine that runs inside your program and
  reads Parquet directly ("SQLite for analytics").
- **Columnar** — stored column-by-column instead of row-by-row, so queries read
  only the columns they need.
- **Deterministic** — same inputs always produce identical outputs.
- **Seed** — the single starting number that makes all the "randomness"
  reproducible.
- **Gravity model** — a retail model where stores attract customers like gravity:
  stronger when closer, weaker with distance.
- **Affinity** — how often two products are bought together (market-basket
  correlation).
- **Tenant / viewer** — the merchant currently looking at the dashboard.
- **The lake** — the privacy-sanitized copy of competitors' data for peer
  comparison.
- **k-anonymity (k=5)** — a privacy rule: only report aggregates covering at least
  5 underlying records, so no individual is exposed.
- **Agentic loop** — the AI working in steps (query → look → query → answer)
  rather than answering in one shot.
- **Claims validator / grounding** — the mechanism that checks every number in the
  AI's answer against the real query results.
- **Anomaly / ground truth** — a deliberately planted business event and its
  hidden answer key, used to test detection.

## 10. Likely engineer questions (and the honest answers)

- **"Why no real database server?"** The workload is read-heavy analytical scans
  over immutable data; embedded DuckDB-on-Parquet is faster, simpler to operate,
  and portable. Production S3/Lambda backends are explicitly deferred.
- **"How do you trust the AI's numbers?"** We don't trust them — we re-verify
  them. The claims validator recomputes every metric against query results and
  strips anything untraceable.
- **"How is competitor data protected?"** Four stacked guarantees: physical
  per-viewer separation with the viewer's rows removed, identity stripping,
  aggregation-only queries enforced on the SQL AST, and a k=5 suppression floor.
- **"Is the data actually realistic?"** It's validated against ~36 acceptance
  bands (volume, AOV, basket correlations, payment mix, pricing spread, promo
  lift) published in `docs/DQ_REPORT.md`.
- **"Can I reproduce a run?"** Yes — same seed yields byte-identical Parquet,
  enforced by the deterministic writer and verified by test T18.
- **"What's the source of truth for the design?"** `docs/DECISIONS.md` (decisions
  D2–D27); the generation spec is `docs/SPEC_wave1_data_generation.md`.
